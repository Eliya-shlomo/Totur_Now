## Scope

**Two failure paths currently drop the user out of the application they were in.** Both are
render-path, both are in the shell, and neither is caught by anything today.

### 1. One throwing screen blanks the whole product

`App.jsx` mounts a single `ErrorBoundary` around `RouterProvider`. A render-time throw in
`Wallet.jsx` unmounts the header, the sidebar, the bottom nav and the route, and replaces
all of it with a centred card whose only control does `window.location.assign('/')`. The
user loses their place, their navigation, and any way to tell which part of the product
broke.

**This PR adds a second boundary inside each shell, around the `Outlet`** — in `AppLayout`
(student, teacher and admin, all three of which are that one file) and in `GuestLayout`.
The outer boundary in `App.jsx` stays exactly as it is: it is what catches a throw in
`AppLayout` itself, and something has to.

Three properties the inner boundary needs and the outer one does not:

- **It resets on navigation.** Once a screen has thrown, the hole must not follow the user
  to the next route. `ErrorBoundary` gains an optional `resetKey`; when it changes, the
  stored error clears. The shells pass `useLocation().pathname`. Without this the inner
  boundary is strictly worse than the outer one — the nav is there and every link is dead.
- **Its way out is "Try again", not a full page load.** The nav is still rendered around
  it, so the user already has ten ways out; what they do not have is a way to re-render the
  one screen that failed. A `window.location.assign('/')` from inside a working shell throws
  away a session the shell was holding for no reason.
- **It says which screen.** The outer card's copy — "This screen hit an error it could not
  recover from" — is about the whole application when the outer one renders it. In the inner
  position it is literally true, and the card sits in the content area at the content area's
  size rather than at `mih="100vh"`.

`ErrorBoundary`'s existing default behaviour must not change, because `App.jsx` keeps using
it unchanged. The new props are optional and the defaults are today's behaviour.

### 2. A logged-in user who mistypes a URL is shown the guest site

There is no `*` route inside `/app`, `/teach` or `/admin`. `routes.guest.jsx` ends in one,
`router/index.jsx` puts the guest array last, and so `/app/nonsense` resolves to
`NotFound` **inside `GuestLayout`**.

Verified in the browser, logged in as a teacher:

    /app/nonsense  →  guest header (Log in · Sign up) · "404 · That page does not exist."
                      · "Back to the home page" → /  · guest footer

No sidebar, no bottom nav, and an invitation to log in offered to somebody who already is.
The definition of done says every failure path shows something a human can read; this one
reads fine and is the wrong product.

**Each area array gains its own `{ path: '*', element: <NotFound … /> }`.** One entry per
file, three files, and `router/index.jsx` — frozen since 0.5 — is not opened. `NotFound`
takes an optional `homeHref` and `homeLabel` so the button inside `/app` goes to `/app`;
the defaults are today's `/` and today's label, so the guest catch-all is unchanged.

### 3. The inline-field-error audit, and its result is that there is nothing to fix

The handoff asked for "the forms that drop `details` on the floor". **There are none**, and
this PR records that rather than inventing one. Audited, every form in the client:

| Form | Server-validated fields | `details` handling |
|---|---|---|
| `Login.jsx` | email, password | `form.setErrors(error.details)` |
| `Register.jsx` | email, password, fullName, role | `setErrors`, **and it steps back to the step that owns the field** |
| `Ask.jsx` | rawText, image | both, per field |
| `Classifying.jsx` | subtopicId | `details.subtopicId`, under the override control |
| `Onboarding.jsx` | per step | `details[field]`, per step |
| `Profile.jsx` | bio, price, level, topics | `details`, keyed by contract field names |
| `RateSession.jsx` | comment (max 1000) | **none — and none can fire.** The `Textarea` carries `maxLength={1000}`, the same number `session.schema.js` enforces, so the field cannot reach the server too long |

The other mutation call sites — `sendOffer` (`{ teacherId }`), `acceptOffer`, `rejectOffer`,
the extend, the top-up (a fixed package list) — carry no user-typed field, so a
`VALIDATION_ERROR` on any of them is a client bug rather than a message to render under a
control. Freeze §4's fourth row already says what those do: a toast.

**The one thing worth writing into code from that audit** is the coupling nobody can see:
`RateSession.jsx`'s `maxLength={1000}` and `session.schema.js`'s `.max(1000)` are the same
rule in two files, and if the server's ever moves, the screen silently starts posting
comments the server rejects into a toast with no field. A comment on each side naming the
other — the same treatment 8.1 gave `PARENT_TOPIC_WEIGHT` and the seed's copy.

## Acceptance criteria

- [ ] A screen that throws on render — force it by editing one page temporarily — shows the error card **inside the content area, with the header, sidebar and bottom nav still rendered and still working**
- [ ] From that state, pressing a nav item navigates and the next screen renders normally. The hole does not follow
- [ ] From that state, **Try again** re-renders the screen without a page load (the network tab shows no document request)
- [ ] A throw in `AppLayout` itself still reaches the outer boundary and still offers **Back to start**
- [ ] `/app/nonsense` while logged in as a student renders 404 **inside the student shell**, with the bottom nav, and the button goes to `/app`
- [ ] `/teach/nonsense` and `/admin/nonsense` do the same for their shells
- [ ] `/nonsense` as a guest is byte-for-byte what it is on `main` — same shell, same copy, same `/` button
- [ ] All four 404s render at 375px with no horizontal scroll
- [ ] `npm test` passes at the count 10.2 left it at; `npx eslint client/src server/src` is clean

1. Log in as `avi.student@demo.tutornow.il` / `TutorNow!2026`.
2. Add `throw new Error('boom')` at the top of `pages/student/Wallet.jsx`'s component. Open `/app/wallet` at 375px.
3. The bottom nav is still there. Press **History** — it loads. Go back to Wallet — still broken, correctly. Press **Try again** — still broken, and no page reload happened.

## Review checklist additions

- **`App.jsx` is not in the diff.** The outer boundary is not moved, not removed, and not
  reconfigured. Two boundaries at two altitudes is the design.
- **`ErrorBoundary`'s defaults are today's behaviour.** Rendering it with no new props must
  produce exactly the card `App.jsx` gets on `main`. Every new prop is optional.
- **`resetKey` is a key, not an effect.** Clearing the error belongs in
  `getDerivedStateFromProps` or a stored previous value — a `useEffect` cannot exist in a
  class component and adding a function wrapper around it to get one is how this file stops
  being the thing that catches throws.
- **Three area files, one entry each.** A `*` added to `router/index.jsx` is a failed review
  — that file is frozen and the split by area is what OWNERSHIP §3.2 is for.
- **The field-error audit's conclusion is "nothing to fix", and a diff that fixes a form
  anyway has found something the audit missed and should say what.**

## Notes

`ErrorBoundary`'s own header already states the limit that matters most here: it catches
render-time throws and **not** event handlers, async callbacks or rejected promises. An
epic called "global error UX" that shipped a second boundary and called the error surface
finished would have improved the rarest failure in the product. The daily half is
`ErrorState` + `notify.apiError`, it is already built, and freeze §4 is where it is written
down.

The 404-in-the-wrong-shell defect has been in the repository since PR 0.5 and survived
five epics, because every one of them tested the routes it added rather than the route
nobody adds.
